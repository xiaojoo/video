# 最大化 / 退出最大化过渡（可复用）

适用：Windows 上"一个渲染窗 + 一个自绘界面窗"的双窗口应用（libmpv / 任意把画面画在
另一个 HWND 里的情况），以及任何"界面窗是附属窗、不能跟着宿主一起被系统搬动"的结构。

参考实现：`player/src/videohost.cpp:96`（批量移动）、`:117`（幕窗）、`:157`（全屏切换，
一次重分配）；`player/qml/Main.qml:158`（`toggleFs()`，四个入口都走它）、`:483`（黑层）、
`:495`（淡出）→ `:509`（停一拍 + 淡入）。

---

## 一、先解决"界面跑到左上角"

症状：点最大化，画面已经到全屏，界面还整屏停在左上角；或者反过来。

这不是画错，是**两个窗不是一次搬的**。原始测量（µs 轮询两个窗的矩形）：

| 做法 | 进入错帧 | 退出错帧 |
|---|---|---|
| 界面靠 60 ms 轮询跟随宿主 | 13 ms | **40 ms**（144Hz ≈ 6 帧） |
| 补一个同步信号，界面走 `QWindow::setGeometry` | 8.0 ms | 8.9 ms |
| 一次 `BeginDeferWindowPos` 批量搬两个窗 | **0** | **23 µs** |

两条结论：

1. **必须批量**。`BeginDeferWindowPos(2)` + 两次 `DeferWindowPos` + `EndDeferWindowPos`，
   两个窗在同一次 Win32 调用里落地。
2. **光"提前通知"不够**。就算信号是直连、在同一个函数里发出来，走 Qt 的 `setGeometry`
   仍要 8 ms（它要重分配渲染表面）。8 ms 在 144Hz 上正好跨一帧，肉眼看得见。
3. 如果渲染方（mpv）替换了宿主窗口的 WndProc，你的 `WM_SIZE` 收不到，跟随只能自己发信号；
   轮询可以留着当兜底，但不能当主路径。

比较的时候要比**渲染窗的客户区**对**界面窗的窗口矩形**，不是两个窗口矩形——真全屏时
窗口本身就在屏外 8 px，比窗口矩形会一直报"不一致"。

## 二、四条死路（都量过，别再走）

### 1. `WS_OVERLAPPEDWINDOW` + 吃 `WM_NCCALCSIZE` + `ShowWindow(SW_MAXIMIZE)`

框架几何没问题：吃掉非客户区后客户区 == 窗口矩形，1282×723 一个像素都不被边框偷。
但：

- **任务栏置顶时，最大化永远盖不住任务栏。** `WM_GETMINMAXINFO` 里要 `-8,-8 3856x2176`，
  `WM_WINDOWPOSCHANGING` 里 Windows 自己给的也是 2176，落地仍是 `3856x2128`——
  夹取发生在窗口过程之后的 win32k 里，应用侧改不动。等于全屏少一条任务栏高度。
  2026-10-18 用**不带** `WM_NCCALCSIZE` 的普通 `WS_OVERLAPPEDWINDOW` 又单独验了一次：
  `WM_GETMINMAXINFO` 给整块监视器 `0,0 3840x2160`，落地还是 `-8,-8 3856x2128`
  （底边 2120 < 2160）⇒ 和框架怎么处理无关，就是系统夹的。
- DWM 的动画**只作用于被最大化的那一个窗**，附属的界面窗会停在终点等画面追上来。

### 2. 自己一步步改窗口矩形做动画

每走一步 = 一次 4K 渲染表面重分配 + 渲染器重建交换链。170 ms 走 21 步，实测步长
中位 7.6 ms、最宽 26 ms ⇒ 144Hz 下必然踩空帧，就是"卡顿"。**改时长、改缓动都动不了
这个单价**，因为它不是节奏问题，是每步的成本问题。

### 3. 用 `video-zoom` / `video-pan-x` 让 mpv 动画画面

属性语义先量清楚（这台机这版 libmpv）：

| 属性 | 实测 |
|---|---|
| `video-zoom` | **log2**：-1 → 画面精确 ×0.5，且以窗口中心为原点 |
| `video-pan-x/y` | 平移量 = pan × **缩放后**的画面尺寸（0.1 在未缩放时移 384/2160 屏的 384 px） |
| `video-offset-x` | 不存在（`property not found`） |

换算：`倍率 s = shown.w / window.w`、`zoom = log2(s)`、
`pan = (shown中心 − window中心) / (s · window尺寸)`。

但**它跟不上时钟**：画面左边缘实测 `2200 → 1253 → 729 → 247`，跨了 190~260 ms，
而时钟只有 170 ms。mpv 对 zoom/pan 的落地是异步的，画面会拖在界面后面。
（另外：改窗口尺寸前必须先把变换设好，否则会先闪一帧终态再弹回起点。）

### 4. 让 mpv 在淡谷里不出画（`video-display=false`）

想法是"让宿主窗自己变黑，就不用管界面重画那条边"。在淡出开始那一刻设 false，重分配在
90 ms 之后——理论上够了。实测**完全没落地**：淡出过程中画面区的亮度斜坡，加这个开关前后
逐格一样（`218/216/215/134/73/0` 对 `219/219/201/134/73/0`），也就是说 90 ms 内 mpv 根本没
把窗口清空，和二.3 是同一种异步。别指望 mpv 的属性当同步刷用。

## 三、最后落地的做法：淡出 → 一次重分配 → 淡入

界面根节点压一层全窗口面纱（`z` 高于界面），淡到谷底的那一拍里做唯一一次批量移动，停一拍，
再淡回来。总长 60 + 24 + 60 = **144 ms**。画面和界面**同时**参与：画面是因为被压暗，界面是
因为盖在它上面——mpv 全程没有被要求缩放，也没有在中途换尺寸。

面纱的**颜色和浓度是一对共享常数**（`VideoHost::dipColor()` / `dipAlpha()`，QML 那层和 Win32
幕窗都读它）。必须共享：两者不一致，幕窗出现的那一帧就是一个可见的台阶。当前取 `#0B0E13`
@ **72 %**，也就是谷底不是全黑，而是"画面被压到 37 % 亮度"。

幕窗（`showCurtain`）只盖界面窗**来不及重画的那一圈**：`outer` 是新旧矩形的并集，`inner` 是
两者中较小的那个（移动之后界面窗已有的缓冲只在较小的那块里还有有效像素），用
`CreateRectRgn` + `RGN_DIFF` + `SetWindowRgn` 挖成 L 形。**不挖洞会更糟**：幕窗的面纱叠在界面
面纱底下再叠一层，实测 0.72 叠 0.72 把谷底从 28 % 压到 **15 %**——白闪变成了黑闪。

实测（录 mp4 + `signalstats` 逐帧读亮度，每帧 8.3 ms，2026-10-18）：

| 量什么 | 数 |
|---|---|
| 按下键 → 窗口矩形改变 | **+71 ~ 76 ms**（淡出 60 + `DwmFlush` 约 11~16） |
| 亮夹具：基线 → 谷底 | 205 → **76**（透出 37 %；叠两层时谷底是 28） |
| 谷底平不平 | `76, 76, 76, 76, 76` 五帧，中途没有更黑的一拍 |
| 洞外那一圈在谷底 | **76**，和画面区同值 ⇒ 遮得一样深，没漏出终态画面 |
| 淡出 / 淡入斜坡 | `205→199→192→124→98→76` / `76→108→128→149→167` |

最后一行左边那格是幕窗存在的意义：窗口一次性变大之后，界面窗新覆盖到的那条边要等 Qt 重画才是
veil 过的，实测 **~14 ms（两帧）**，在那之前透出来的是**没压暗的终态画面**（205 而不是 76），
等于压暗到一半全屏亮一下——这就是"闪一下"。GDI 的类画刷在 `SetWindowPos` 调用里就填完了，
不等任何一次重画，所以由它来挡。

### 幕窗必须 `UpdateWindow` + `DwmFlush`，少一个都还是闪

`UpdateWindow` 只保证这一帧**画进了窗口表面**，不保证**合成器已经收下它**。差一帧的结果是
随机的：幕窗的早一步到屏，就没事；晚一步，就正好露出重分配之后的终态画面一帧。

第一次交付就是这么翻的车——他 PixPin 录的 60 fps 里，`f144` 还是窗口化（整屏均值 27），
`f145` 已经是**全屏画面 + 界面窗留在旧位置旧尺寸的残影**（75.6），`f146` 才是全黑（16.8）。
一帧 16.7 ms，肉眼就是"闪一下"。用他自己的片子（暗）当夹具才看得出来——用我自己那份亮夹具
`edge.mp4`，窗口化和全屏的均值都是 170 上下，**这把尺子根本分辨不出泄漏**，所以我前一轮
"360 帧没有一帧亮过 200"的结论是无效结论。

修法是在 `moveBoth` 之前 `UpdateWindow(m_curtain)` 之后再加一次 `DwmFlush()`（dwmapi）：
它阻塞到当前帧被合成，代价最多一个 vsync。改完连测三次，旧矩形外那一圈都是
`36 → 0` 并且过零之后不再变亮（重分配时刻 +0.109 ~ +0.115 s，比加 flush 前的 +0.093 晚约
15 ms，被 40 ms 的淡谷吸收）。

**教训：证"没有闪"要用会被闪扰动的夹具。** 暗片子配亮画面才有分辨力；亮片子内和外都亮，
数出来永远是"没闪"。

### 为什么不做真缩放

真缩放要么复制一份画面，要么让渲染器自己缩。三条都量过：

- **`video-zoom` 让 mpv 缩放**：跟不上时钟，见二.3。
- **快照**（DWM 的最大化动画内部就是这张图）：抓 **1282×721 中位 55.6 ms**（最快 53.8 /
  最慢 71.0），而抓整块 **3840×2160 才 61.9 ms** ⇒ 这是 GDI 拷屏的固定开销，**区域小省不
  下来**，等于按下键之后先空等 56 ms 动画才起步。更致命的是拷屏拿到的是 DWM 合成之后的
  **SDR**：HDR 片段在这 220 ms 里要掉一次色。为保 HDR 才选的双窗口架构，不该每次进出全屏
  都牺牲一次颜色。
- **步进重分配**：21 次 4K 重分配、一步最长 26 ms，见二.2。

溶接这条一个都不欠：不拷屏、不步进重分配、mpv 不动，而黑色在 SDR 和 PQ 里都是 0。

### 留下的三条

1. **一次批量搬两个窗**（一、）。这是全部收益的来源，也是唯一必须保留的机制。
2. 进入前存 `m_restoreRect`，退出回到它。`toggleFullscreen()` 里
   `moveBoth → emit resized → emit fullscreenChanged` 这个顺序别动：跟在
   `fullscreenChanged` 上的"按影片比例吸窗口高度"要读到已经提交的矩形。
3. 淡出/淡入进行中要挡住重复触发（`toggleFs()` 判两个动画的 `running`），否则连按 F 会把
   重分配安排在半透明的帧上。

## 四、量具怎么搭

- **µs 级时间线**：另起进程用 `GetWindowRect`/`GetClientRect`+`ClientToScreen` 忙等轮询，
  `sys.setswitchinterval(1e-5)`，**不要 sleep**（4 ms 的 sleep 会把真延迟和量化混在一起）。
  ctypes 调用会释放 GIL，所以忙等不会饿死主线程。
- **合成鼠标/键盘必须真游标**：`SendInput`；键盘事件要和鼠标事件放**同一个 union**，
  自己拼 `{DWORD; KEYBDINPUT}` 会把成员放到偏移 4（真 `INPUT` 因指针对齐是 8），
  `SendInput` 直接返回 0，然后你会把"我的按键没进去"读成"应用没反应"。每次都要查返回值。
- **抓屏测位置**：采样间隔要远小于被测周期（170 ms 的过渡用 55 ms 的抓屏只有 3 个点，
  结论会假）；测"界面在不在"要挑一个全程都在视野里的特征（右上角按钮的 x 扫描），
  别用"左上角有没有白像素"——界面一大那块就本来就空了。
- **别用点击激活窗口**：如果单击画面区会切界面显隐，你的探针就自己把被测对象关了。
- 报"某个控件坏了"之前，先给它一条**不经过你的点击**的到达路径（环境变量开关 / 直接调用），
  两条都断才是控件坏。
